 Reason for Change

Asia Cement Public Company Limited (referred to in this proposal as ACC)
has an existing solution, the SAM web app, that is currently being
development by Manao Software. The current PAM proposal and rebate
workflow has three gaps that create process misalignment with ACC rules
and avoidable user friction.

Currently, the SAM system treats each proposal as an independent entity.
Proposals can be created and approved individually by managers without
dependency on other proposals. However, when synchronizing approved
proposal data back to the SAP system, there are several restrictions and
business rules that must be enforced.

These constraints have resulted in data inconsistencies and limitations
in the current synchronization process. Therefore, an enhancement to the
SAM backend service is required to properly store proposal data, process
business logic through stored procedures, and synchronize accurate and
compliant data back to SAP.

Together, these changes are needed to align PAM with ACC’s operating
model, reduce calculation risk, and streamline the proposal user
experience.

Proposed Solution

Manao Software will provide software development resources to design,
implement, test, deploy, and maintain the requested Change Request (CR)
for the ACC system. This document describes the implementation approach,
understanding of the scope, proposed technical solution, and the
associated delivery schedule and cost.

The PAM system will be enhanced through two coordinated system
improvements to align proposal structuring, rebate governance, and
date-handling behavior with ACC’s defined business processes.

First, PAM will support proposal data consolidation to enable accurate
data persistence in the forcal table. This enhancement ensures that SAP
synchronization and agreement calculation processes can be executed
correctly and consistently.

Second, PAM will introduce logic to evaluate customers appearing across
multiple proposal types. When a customer exists in both Proposal Type R
and Proposal Type S within the same evaluation period, the system will
apply a defined priority rule and synchronize Proposal Type S data to
ACC SAP for discount and rebate calculation, while suppressing Proposal
Type R data for that customer. This logic ensures consistent processing
and removes ambiguity during monthly calculation cycles.

3.1: Multiple Proposal Data Merge

  Currently, the SAM system treats each proposal as an independent
  entity. Proposals can be created and approved individually by managers
  without dependency on other proposals. However, when synchronizing
  approved proposal data back to the SAP system, there are several
  restrictions and business rules that must be enforced.

  These constraints have resulted in data inconsistencies and
  limitations in the current synchronization process. Therefore, an
  enhancement to the SAM backend service is required to properly store
  proposal data, process business logic through stored procedures, and
  synchronize accurate and compliant data back to SAP.

Proposal Type P: Conditions

- Proposal Type P does not involve rebate processing.

- Data from Proposal Type P will not be stored in the forcal table.

- SAP synchronization is limited to non-rebate related data only.

Proposal Type P – Flow 2 and Flow 3

- Users must create separate proposals for each combination of:

  - Customer Group

  - Ship-to

This separation is required so that SAM can validate the correct
contract number from SAP.

Example:

- Customer Group 1 + Ship-to A → Contract No. A

- Customer Group 1 + Ship-to B → Contract No. B

Proposal Type R: Conditions

Flow 1 – Discount Only

- Discount-only proposals have no impact on SAP because SAP can
  automatically split discount periods by date.

- When discount values change during an active period, users must create
  new proposals with adjusted date ranges and versions.

Example:

- Proposal R #001 (Version 0): Jan 1–31, Discount 5 THB/ton (Approved)

- Proposal R #001 (Version 1): Jan 1–12, Discount 5 THB/ton

- Proposal R #002 (Version 0): Jan 13–31, Discount 8 THB/ton

Each proposal must be submitted and approved separately.

Flow 4 – Rebate + Accumulate

- Rebate proposals require strict handling and synchronization with SAP.

- When a rebate value changes, proposals must be split by date range.

- Upon approval:

  - Active proposals are inserted into the forcal table.

  - Inactive or superseded proposals are removed from forcal.

Key Attributes:

- Sales Organization

- Sold-to

- Proposal Month (pmonth)

- Proposal Year (pyear)

- Rebate Type

- From Date

- To Date

Proposal Type S: Conditions

Flow 1 – Discount + Special Accumulate

- Discount logic behaves similarly to Proposal Type R.

- SAP can handle date splitting automatically.

- Special Accumulate values are tied to the proposal date range.

Example:

- Proposal S #001 (Version 0):

  - Jan 1–31, Discount 5 THB/ton

  - Special + Accumulate: 10 THB (Approved)

If changes occur mid-period:

- Proposal S #001 (Version 1): Jan 1–12, Discount 5 THB/ton, Special +
  Accu 10 THB

- Proposal S #002 (Version 0): Jan 13–31, Discount 8 THB/ton, Special +
  Accu 20 THB

Flow 4 – Rebate + Accumulate

- Similar to Proposal Type R Flow 4, but includes Special Accumulate.

- Upon approval:

  - Discount and rebate data are inserted into forcal.

  - Inactive proposals are removed.

Key Attributes:

- Sales Organization

- Sold-to

- Proposal Month (pmonth)

- Proposal Year (pyear)

- Rebate Type

- From Date

- To Date

Out of scope

- Proposal range overlapping validation, since Frontend UX/UI are not
  updated

- Any change to ACC monthly proposal policy.

- Any SAP-side enhancement to support the new structure.

3.3: Proposal Priority Rules

This part enforces Proposal Type S Has Priority Over Proposal Type R. At
the current SAP workflow, it would check following attributes and update
approved discount or rebate regardless to the proposal priority and
could cause incorrect data. Then the additional backend services need to
handle the case as follows:

Key Attributes for Priority Check:

- Proposal Month (pmonth)

- Proposal Year (pyear)

- Sales Organization

- Sold-to (Customer Code)

Scenario 1: Proposal R Approved First, Then Proposal S

1.  Proposal R is approved:

    - SAM synchronizes data to SAP (Flow 1 and above).

2.  Proposal S is approved afterward:

    - SAM synchronizes Proposal S data to SAP, overriding Proposal R
      data.

    - Proposal R records are removed from the forcal table.

Scenario 2: Proposal S Approved First, Then Proposal R

1.  Proposal S is approved:

    - SAM synchronizes data to SAP.

2.  Proposal R is approved afterward:

    - SAM checks if the customer exists in an approved Proposal S.

    - If yes:

      - Proposal R is ignored.

      - No SAP synchronization occurs.

      - No data is inserted into forcal.

Backend Service Enhancement Required

- Store proposal versions and activation status accurately.

- Implement logic for proposal splitting by date range.

- Enforce priority rules between Proposal S and Proposal R.

- Insert only active proposals into forcal.

- Automatically remove inactive or superseded proposals from forcal.

- Ensure SAP synchronization follows defined business flows.

Out of scope

- Any change to ACC rebate formulas or calculation engine behavior.

- New proposal types or customer hierarchy/roll-up rules beyond R/S.

- Retroactive reprocessing of historical rebate periods unless
  explicitly requested later.
